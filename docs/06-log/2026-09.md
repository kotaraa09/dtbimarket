2026-09-03  D-2 decided: server-side session, not JWT. The argument that settled it was not the usual one about `localStorage` being script-readable — it was revocation. A seller who withdraws from the study has to be signable-out, and a self-contained token cannot be taken back. Sessions are a table; `node:crypto` HMAC signs the ID into an httpOnly cookie. No session library (rule 10).

2026-09-03  Append-only enforcement needed a fourth mechanism, not three. ADR-0001 says the application refuses, the database role has no `UPDATE`/`DELETE` grant, and review looks for it. But **a table's owner bypasses its own grants**, and in local development and the simplest managed-Postgres setups the app connects as the owner — so the grant was protecting nothing here. Added a `BEFORE UPDATE OR DELETE` trigger that raises regardless of who is connected, and kept the grants for deployments with a separate role. Verified by test: both statements now fail with the rule quoted in the error.

2026-09-03  Found and fixed a data-integrity bug the hard way: an action taken on a **seed** store was writing `is_seed = false` events. Every analysis query and every seller-facing metric would have counted demo activity as real, and the only reason it surfaced was checking the table after clicking through the UI rather than trusting the 200. `is_seed` now propagates from the acting store (or user, before a store exists) into the event. One wrong row from before the fix is still in the local dev database and always will be — which is the append-only lesson at one row's cost, so it is being kept rather than reset away.

2026-09-03  `parseBahtToSatang` accepted `"12,"` as 12 baht. It stripped every comma and then validated, so any comma placement passed. Caught by a test written for the round-trip property, not by anything anyone noticed on screen. Now the separators have to be in valid thousands positions or the input is refused. Money bugs do not throw; they just make a seller's totals disagree with their own arithmetic.

2026-09-03  Bug found in testing, not in review: an oversize upload was destroying the socket, so the client saw a connection reset instead of the 413 that `api-spec.md` specifies. A seller uploading a 6 MB photo from their phone would have been told "something went wrong" rather than "your photo is too big". The fix is to drain the request instead of destroying it — a client mid-upload cannot read a response on a socket that has already been torn down. Now rejected on `Content-Length` where it is honest, with a streaming cap as the backstop and a hard limit before the connection is genuinely abandoned.

2026-09-10  **Privilege escalation found in code I wrote in the previous session.** `registerSchema` accepted `role` from the request body with `admin` in the allowed values, and the handler wrote it through — so `POST /auth/register {"role":"admin"}` on a public, unauthenticated endpoint created an administrator. Being accurate about the blast radius: it granted nothing at the time, because `admin` only passed `requireSeller` and every route behind it then scoped to the caller's own store, which an admin has none of. It became a real escalation the moment `admin` meant anything — which is what this session added. Registration now accepts `seller` and `buyer` only; administrators come from `pnpm admin:create`. The general lesson is that a public endpoint must never accept a privilege-bearing field, however harmless the privilege is on the day it is written.

2026-09-10  `requireSeller` used to admit `admin`, and that was only safe by accident: the store lookup that followed refused an admin because they have no store. Relying on a second guard to catch what the first should have refused stops being true the moment someone adds a route that does not do the second check. It is seller-only now, and admins have their own area.

2026-09-10  Admin sign-in was being recorded as `buyer.signed_in`. The login handler branched `role === 'seller' ? seller.signed_in : buyer.signed_in`, so every other role fell into the buyer bucket — operator activity counted as buyer behaviour, in an append-only table that cannot be corrected. Fixed before any admin existed, so no rows were affected. Worth remembering as a shape: a two-way ternary over a three-value enum is a silent miscategorisation, not an error.

2026-09-10  **ADR-0005, and a decision I recommended wrongly.** I proposed keeping admin actions out of `Event` and letting the `User` row be the record — status, changed-at, changed-by. The owner asked whether a compromised admin could still be traced. The answer was no: reads leave nothing at all, which matters because reading personal data is the admin area's entire purpose; and single columns are overwritten, so suspend-then-reinstate erases the suspension. I had conflated "do not pollute the research data" with "do not record it anywhere" and offered a false choice between two options when the right answer was a third. Now a separate append-only `AdminAuditLog`, same trigger technique as `event`, recording reads as well as writes, with metadata holding field *names* and never values.

2026-09-10  Anonymisation (REQ-N21) does not touch `Event`, and does not need to. That is REQ-N2 paying for itself: because events reference people by ID and hold no personal data, erasure and append-only telemetry coexist instead of contradicting each other. The test asserts the event count is unchanged across an anonymisation — the property is easy to break silently and impossible to repair afterwards.
